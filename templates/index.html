Why a Binary Min-Heap?

In production cloud scheduling and emergency operating systems, sorting an entire database table on every insertion is prohibitively expensive ($\mathcal{O}(n \log n)$). A Binary Min-Heap maintains a semi-ordered complete binary tree where every parent node has a priority value smaller than or equal to its children ($A[\text{parent}] \le A[\text{child}]$).

This guarantees that the root (index 0) is always the highest-urgency task in $\mathcal{O}(1)$ time, while insertions and extractions only require walking the tree height ($\mathcal{O}(\log n)$).

Time Complexity Comparison

Operation Min-Heap Unsorted Array Sorted Array
Peek (Root) O(1) O(n) O(1)
Insert (Enqueue) O(log n) O(1) O(n)
Extract-Min (Dispatch) O(log n) O(n) O(1)
Update Priority (Sift) O(log n) O(1) search + O(1) O(n)

Zero-Pointer Array Flattening Formulas

Parent Index: floor((i - 1) / 2) Left Child Index: 2 * i + 1 Right Child Index: 2 * i + 2 Min-Heap Invariant: A[floor((i - 1) / 2)] ≤ A[i] for all valid child indices i > 0. Ordering Rule: First: lower numeric priority (P1 Critical before P4 Low). Second: earlier persistent insertion sequence for equal priorities (FIFO stability). Key Insight: A binary min-heap does NOT store every element in fully sorted order! It guarantees ONLY that its root (index 0) is the highest-priority eligible element under the chosen ordering rule.
